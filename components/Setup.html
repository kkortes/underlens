Add it to a repo

Four steps and three files. Most repos need to change only the rules.

1 Write the three files

bunx @ape-egg/underlens init

This writes the three files below into your repo and leaves any that already exist alone.

underlens.config.js

Which harnesses review and which one judges. The defaults are Claude for both.

underlens-quality-control.md

Your rules. Replace the starter set with what your team actually holds code to, numbered, one decidable claim each.

.github/workflows/underlens.yml

The triggers and one step that runs the package. The triggers decide when PRs are reviewed: the template reviews once a night at the cron hour, in UTC. Add opened and reopened to review each PR as it opens, or drop schedule to review only when you ask.

2 Add a secret per harness

One per harness in underlens.config.js. See the instructions for each one. With the default config, that's:

claude setup-token gh secret set CLAUDE_CODE_OAUTH_TOKEN

3 Let workflows open pull requests

The fixes arrive as PRs, and GitHub only lets workflows open PRs once you allow it: Settings → Actions → General → "Allow GitHub Actions to create and approve pull requests". Or from the repo folder:

gh api -X PUT repos/{owner}/{repo}/actions/permissions/workflow -F can_approve_pull_request_reviews=true

4 Commit, then check every harness

Push the three files to your default branch, then run the workflow by hand with no PR number. It signs in to every configured harness, asks each one for a one-word answer, and reports per harness whether it's ready for the next run. The run fails until every harness is ready.

Not ready: fix the rows above, then run this again.

From then on

  • Every PR gets its Underlens section once it's reviewed, on the triggers your workflow lists.
  • To review a PR right away, or review it again: Actions → Underlens → Run workflow, with its number. Each review starts fresh and closes the fixes left open from the last one.
  • The schedule skips draft PRs until they're ready for review. PRs from forks aren't reviewed, because the fixes need a branch in your repo.
  • Fix PRs opened by the workflow don't trigger your other workflows, which is GitHub's rule for its token. Your CI runs once you merge the agreed fixes into your PR.
