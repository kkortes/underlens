How it works

One pull request, from the moment it opens to the moment you decide.

 1

You write the rules

underlens-quality-control.md is a numbered list of rules, each one decidable: a reviewer can point at a line and name the rule it breaks. A person curates it. It's the only standard Underlens holds code to, so taste no rule decides is never raised.

underlens-quality-control.md
  1. No console.log in committed code.
  2. No commented-out code.
  3. No try/catch that swallows an error.
  4. No dependency for what a few lines would do.
 2

Your workflow says when

The triggers in .github/workflows/underlens.yml decide when a PR is reviewed. A schedule reviews every open PR not reviewed yet. A PR opening reviews it at once. Run workflow reviews one on demand. List the ones you want. The template reviews once a night.

.github/workflows/underlens.yml
  1. schedule: every open PR not reviewed yet, at the cron hour
  2. pull_request opened: that PR, right away
  3. workflow_dispatch: the PR of the branch you run it on
 3

Reviewers run side by side

When the time comes, one agent per configured reviewer starts in CI and does a full review. Each reads the quality document first, then the PR's diff, then as much of the codebase as it needs. Each one reports only where the PR breaks a numbered rule. A reviewer that fails doesn't stop the others: the review goes on with those that answered, and the PR says which one failed and why.

@[lane.harness] rulesdiffcodebase @[lane.findings] findings 4

A judge turns them into points

One judge reads every report. Findings about the same rule in the same place become one point, however differently they were worded. Any finding the code doesn't actually support is dropped. Each point is named after its rule and its place, so drift that stays reads the same on every review. With no report to read, or a judge that fails, the PR keeps its last review or says this one failed, and the run fails.

@[finding.harness] @[finding.at] → Rule 3 · api.js Rule 1 · cart.js Rule 4 · package.json 5

Every point becomes its own fix PR

Underlens cuts a branch from the PR, underlens-pr-42, and the judge writes one fix per point. Each fix becomes its own small PR into that branch, so you can take one fix and leave another.

feature/checkout #42 underlens-pr-42 underlens-pr-42-rule-3-1 #43 underlens-pr-42-rule-1-2 #44 underlens-pr-42-rule-4-3 #45 6

The PR's section becomes the report

The section in the original PR is replaced with a short status report: one block per point, naming the rule it breaks, saying what its fix changed and linking to it. Each block has an Agree box and a Disagree box. Once reported, the PR isn't reviewed again unless you ask for it by hand.

You have three choices

Disagreeing doesn't make a point go away. The rule still says what it says, so the same point comes back on the next review, and it keeps coming back until the code or the document changes. That's by design: drift should keep nagging until a person settles it.

Agree

The fix merges into underlens-pr-42, which comes back to your PR as one PR of its own.

Disagree

The fix PR closes. The code stays as it is, and the reminder returns on the next review.

Change the rule

Edit the quality document. The rule no longer says it, so the agents stop raising it.
